# Energy Map: контекст масштабного застосування ГПВ

Основне джерело проєкту — НКРЕКП. Energy Map додається лише як контекст.
Джерело: [Energy Map — інформація щодо застосування заходів обмеження споживання електроенергії](https://energy-map.info/uk/datasets/0f8f9882-1fb2-47c6-81dc-31fbad914f16).
[Документація API](https://energy-map.info/uk/docs/api/).

## Що налаштовано

`Update Energy Map outages` запускається 5-го числа кожного місяця о 08:37 UTC
та вручну через Actions. Push коду не запускає завантаження. Якщо джерело вже
успішно перевірено цього календарного місяця UTC, запит пропускається.
Це наше правило економії; спосіб обчислення місяця у тарифі Energy Map невідомий.
Повторний запуск того самого workflow run заблоковано, автоматичних повторів і
переходів за HTTP-перенаправленням немає. Окремий новий ручний запуск після
невдалої спроби може витратити ще один запит — спочатку перевірте причину помилки.

Потрібен repository secret **ENERGY_MAP_TOKEN**:
Settings → Secrets and variables → Actions → New repository secret.
Вставляти лише значення токена (без префікса Token). Код додає префікс сам.
Токен не зберігається у файлах і не виводиться в логах. Без секрету належний
за датою запуск завершиться помилкою до звернення до API.

Успішний тест 21.10.2026 о 15:38 UTC витратив 1 API-запит і 1 завантаження:
лічильники 0/10 → 1/10 та 1/10 → 2/10 відповідно. Відповідь HTTP 200,
application/octet-stream, 1 292 323 байти; CSV побайтово збігся з ручною копією.
Саме цю відповідь додано як початковий знімок; додаткового API-запиту не було.
Перша планова перевірка після налаштування — 05.11.2026.

## Збереження та перевірки

- `data/energy_map/current.json` — поточний SHA-256, шлях до оригіналу,
  початкова/остання дата записів, кількість рядків, остання успішна перевірка.
- `data/energy_map/raw/<sha256>.csv` — оригінальні байти CSV.
- Однаковий SHA-256 → новий знімок не створюється; дата перевірки оновлюється.
- Новий SHA-256 → знімок архівується після перевірки UTF-8, заголовка,
  кількості полів, наявності датованих рядків і формату непорожніх дат. Це технічна перевірка,
  а не підтвердження аналітичної якості даних.
- Помилка HTTP або неочікуваний CSV → попередня прийнята версія залишається;
  дата успішної перевірки не оновлюється. Коміт виконується лише після успіху.
- `last_changed_at_utc` — коли проєкт уперше побачив цю версію, не дата
  публікації постачальника. `last_check_changed` — результат останнього порівняння.

Для дашборду: `data_end_date` — остання дата даних,
`last_checked_at_utc` — остання успішна перевірка джерела. Це різні показники.
Початковий файл містить записи до **30.06.2026** включно; дата назви 01.07.2026
не є останнім спостереженням.

У початковому CSV виявлено 328 рядків без дати та посилання на Excel-комірки
у полі годин. Оригінал не виправляється; кількості таких рядків наведено
в `missing_date_rows` та `formula_hour_rows`. Межі дат обчислюються лише
за непорожніми датами й не доводять повноти часового ряду.

## Підготовка даних із навчального ноутбука

Логіку авторки з `energy_map_outages_cleaning.ipynb` перенесено до
`scripts/prepare_energy_map.py`. Читабельна версія ноутбука:
[`notebooks/energy_map_outages_cleaning.ipynb`](../notebooks/energy_map_outages_cleaning.ipynb).
Ноутбук читає збережений знімок через `current.json`, а не фіксовану назву файлу;
мережевих запитів у ньому немає. У Colab спочатку завантажте репозиторій і залежності
за інструкцією на початку ноутбука.

Плановий workflow: **один API-запит → SHA-256 → обробка лише нової або pending-версії**.
Також обробка повторюється після зміни `PROCESSOR_VERSION`, відсутності або зміни
очищеного CSV. Для змін методики підвищуйте цю версію в модулі.
Ручний запуск Actions за замовчуванням виконує лише офлайн-підготовку.
Поле `check_source` треба увімкнути явно для звернення до API; місячний запобіжник
і заборона повторного workflow run залишаються чинними.

Результати:
- `data/energy_map/processed/outages.csv` — очищені погодинні записи (UTF-8 із BOM).
- `data/energy_map/processed/audit.json` — кількості, SHA джерела та припущення.
- `current.json`: `processed_sha256`, `processor_version`, `last_prepared_at_utc`,
  `processed_file_sha256`, `processed_file`, `preparation_pending`.

Дата підготовки не підмінює дату перевірки API. Для дашборду використовуйте окремо
`data_end_date` та `last_checked_at_utc`. Якщо `preparation_pending: true` або
`processed_sha256 != sha256`, очищена таблиця ще відповідає попередньому джерелу:
її дату покриття дивіться в `processed/audit.json`, а на дашборді показуйте попередження.

При помилці підготовки старий очищений CSV зберігається. Workflow все одно комітить
прийнятий оригінал і дату успішної перевірки API з pending-позначкою, потім залишається
невдалим. Це дозволяє виправити обробку і повторити її без нового завантаження.
Якщо сам запис коміту в GitHub не вдався, дата перевірки не буде збережена віддалено;
перед новим ручним API-запуском перевіряйте логи та лічильники профілю.

### Правила очищення

1. Рядки не видаляються. Порожній обсяг при `outage_use == 'ні'` стає нулем.
   При `так` невідомий обсяг зберігається як пропуск.
2. `number` перейменовується на `outage_coverage`: це географічне охоплення,
   а не кількість черг. Порожнє охоплення при `ні` → «не застосовувались»;
   при `так` новий пропуск залишається невідомим.
3. `outage_amount` описує черги, які відключають одночасно. Початковий текст
   зберігається (крім погодженого заповнення нулями); додаються мінімум і максимум.
   Одна цифра потрапляє в обидві межі, «від A до B» → A/B,
   «до B» → 0/B. **Нульова нижня межа для «до» — наша аналітична домовленість**.
4. Авторські категорії, не офіційна шкала: 0/0 — «Без обмежень»;
   0 < min і max ≤ 1 — «Низька»; 1 < min і max ≤ 2 — «Помірна»;
   min > 2 — «Висока»; інший відомий діапазон — «Кілька рівнів»;
   невідома межа — «Невідомо». «Кілька рівнів» означає перетин кількох рівнів,
   а не доведену зміну в часі. Категорії не визначають години без світла за адресою.
5. Перевіряються всі дати й точний набір погодинних інтервалів кожної доби
   за `Europe/Kyiv`, включно з 23/25-годинними днями. Осінній повтор години зберігається.
   Невідомий формат обсягу, суперечність статусу та обсягу або новий часовий дефект
   потребують ручного розгляду. Це не зовнішнє підтвердження правильності статусів.

### Відновлення 328 квітневих дат — припущення

Між `2026-03-31 23:00-00:00` та `2026-04-14 16:00-17:00` знайдено 328 рядків
без дати, з послідовними Excel-посиланнями у `hour`. Їхня кількість збігається
з погодинним проміжком 01.04.2026 00:00–14.04.2026 15:00.
Дату й інтервал призначено за порядком рядків; `datetime_reconstructed=True`.
**Постачальник це відновлення не підтверджував**. Статуси, обсяги й географічне
охоплення не переставляються. 278 рядків мають «ні», 50 — «так» з невідомим обсягом.
Для аналізу чутливості можна окремо виключати позначені записи.

Виправлення знаходить межі за значеннями, а не за індексами. Застосовується лише
до повного впізнаного дефекту; інші пропуски зупиняють підготовку. Якщо постачальник
виправив усі дати або надав файл іншого періоду без пропусків, реконструкція не запускається.
Оригінальний CSV незмінний; `missing_date_rows` у current.json описує саме оригінал.

Локальна підготовка без API:
```bash
python -m pip install -r requirements.txt
python -m scripts.prepare_energy_map
python -m unittest discover -s tests -p '*energy_map*.py' -v
```

Для збереженої відповіді в окремому тестовому каталозі:
```bash
python -m scripts.collect_energy_map --from-file /path/to/electricity_outages.csv --data-dir /tmp/energy-map-replay
python -m scripts.prepare_energy_map --data-dir /tmp/energy-map-replay
```
Офлайн replay ставить тестову дату перевірки; не використовуйте його для підміни
справжньої дати перевірки у робочому каталозі.

## Обмеження та використання

Це історія масштабного застосування графіків, а не фактична тривалість відсутності
світла за адресами. Локальні ГПВ у 1–3 областях не враховуються.
За 10.12.2025–28.01.2026 дані узагальнено за інформацією обленерго.
Постійний лаг безкоштовної версії у три місяці не підтверджено.
За переданою умовою п. 6.1.5 безкоштовний контент використовується з обов'язковим
гіперпосиланням на Energy Map, якщо немає окремої ліцензії; посилання наведено вище
та має бути також на дашборді.

ENTSO-E не підключено цим workflow: заявка #9475179 і дозвіл на використання
12.1.d / 12.1.f залишаються на очікуванні відповіді.
